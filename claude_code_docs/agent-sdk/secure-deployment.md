# AI 에이전트 안전하게 배포하기

> 격리 환경, 자격 증명 관리 및 네트워크 제어를 통해 Claude Code 및 Agent SDK 배포의 보안을 강화하는 가이드

Claude Code 및 Agent SDK는 사용자를 대신해 코드를 실행하고, 파일에 접근하며, 외부 서비스와 상호작용할 수 있는 강력한 도구입니다. 이러한 기능을 가진 다른 모든 도구와 마찬가지로, 이를 신중하게 배포하면 적절한 제어를 유지하면서 그 이점을 최대로 누릴 수 있습니다.

미리 정해진 코드 경로를 따르는 기존 소프트웨어와 달리, 이 도구들은 컨텍스트와 목표에 따라 동적으로 동작을 생성합니다. 이 유연성이 도구를 유용하게 만들지만, 동시에 파일, 웹페이지, 사용자 입력 등 처리하는 콘텐츠에 의해 동작이 영향받을 수 있음을 의미합니다. 이를 프롬프트 주입(prompt injection)이라고 부르기도 합니다. 예를 들어 저장소의 README에 비정상적인 지시가 포함된 경우, Claude Code는 작업자가 예상하지 못한 방식으로 해당 지시를 동작에 반영할 수 있습니다. 이 가이드에서는 이러한 위험을 줄이는 실용적인 방법을 다룹니다.

다행히 에이전트 배포의 보안을 강화하는 데 특별하고 생소한 인프라가 필요한 것은 아닙니다. 반쯤 신뢰할 수 있는 코드를 실행할 때 적용되는 기본 원칙, 즉 격리(isolation), 최소 권한(least privilege), 심층 방어(defense in depth)가 동일하게 적용됩니다. Claude Code에는 일반적인 우려 사항을 해결하는 여러 보안 기능이 내장되어 있으며, 이 가이드에서는 필요한 사용자들을 위해 이러한 기능과 함께 추가적인 보안 강화 옵션을 소개합니다.

모든 배포에 최고 수준의 보안이 필요한 것은 아닙니다. 노트북에서 Claude Code를 실행하는 개발자와 멀티 테넌트 환경에서 고객 데이터를 처리하는 기업은 요구 사항이 다릅니다. 이 가이드에서는 Claude Code의 내장 보안 기능부터 강화된 프로덕션 아키텍처에 이르기까지 다양한 옵션을 제시하므로 상황에 맞는 최선의 선택을 할 수 있습니다.

## 위협 모델 (Threat model)

에이전트는 프롬프트 주입(처리하는 콘텐츠에 삽입된 지시사항)이나 모델 오류로 인해 의도하지 않은 행동을 취할 수 있습니다. Claude 모델은 이러한 시도에 저항하도록 설계되었습니다. 평가 세부 내용은 [모델 개요](https://platform.claude.com/docs/en/about-claude/models/overview) 및 배포하려는 모델의 시스템 카드를 참고하세요.

그럼에도 불구하고 심층 방어 조치는 훌륭한 관행입니다. 예를 들어 에이전트가 고객 데이터를 외부 서버로 전송하도록 지시하는 악성 파일을 처리하더라도, 네트워크 제어가 설정되어 있다면 해당 요청을 완전히 차단할 수 있습니다.

## 내장 보안 기능

Claude Code에는 일반적인 우려 사항을 해결하는 여러 보안 기능이 포함되어 있습니다. 자세한 내용은 [보안 문서](/docs/en/security)를 참고하세요.

* **권한 시스템**: 모든 도구 및 bash 명령어를 허용, 차단 또는 사용자에게 승인 요청하도록 구성할 수 있습니다. 글로브 패턴을 사용하여 "모든 npm 명령 허용" 또는 "sudo가 포함된 모든 명령 차단"과 같은 규칙을 만들 수 있습니다. 조직 차원에서 모든 사용자에게 적용되는 정책을 설정할 수도 있습니다. [권한](/docs/en/permissions)을 참고하세요.
* **권한 검사를 위한 명령어 파싱**: bash 명령어를 실행하기 전에 Claude Code는 이를 AST로 파싱하고 설정된 권한 규칙과 일치하는지 확인합니다. 명확하게 파싱되지 않거나 허용 규칙과 일치하지 않는 명령어는 명시적인 승인이 필요합니다. `eval`과 같은 일부 구문은 허용 규칙에 관계없이 항상 승인을 요구합니다. 이것은 권한 게이트일 뿐 샌드박스가 아니므로, 대상 경로나 영향으로부터 명령어가 위험한지 여부를 추론하지는 않습니다.
* **웹 검색 요약**: 원시 콘텐츠를 컨텍스트에 직접 전달하는 대신 검색 결과를 요약하여 제공하므로, 악성 웹 콘텐츠에 의한 프롬프트 주입 위험을 줄입니다.
* **샌드박스 모드**: bash 명령어를 파일 시스템 및 네트워크 접근이 제한된 샌드박스 환경에서 실행할 수 있습니다. 자세한 내용은 [샌드박스 문서](/docs/en/sandboxing)를 참고하세요.

## 보안 원칙

Claude Code의 기본값을 넘어 추가 보안 강화가 필요한 배포의 경우 다음 원칙들이 도움을 줍니다.

### 보안 경계 (Security boundaries)

보안 경계는 신뢰 수준이 서로 다른 구성 요소를 분리합니다. 높은 보안이 필요한 배포의 경우 민감한 리소스(자격 증명 등)를 에이전트가 포함된 경계 외부에 둘 수 있습니다. 에이전트 환경 내에서 문제가 발생하더라도 경계 외부의 리소스는 보호된 상태로 유지됩니다.

예를 들어 에이전트에 API 키 직접 접근 권한을 주는 대신, 에이전트 환경 외부에 프록시를 실행하여 요청 시 키를 주입하도록 할 수 있습니다. 에이전트는 API를 호출할 수 있지만 자격 증명 자체를 보지는 못합니다. 이 패턴은 멀티 테넌트 배포나 신뢰할 수 없는 콘텐츠를 처리할 때 유용합니다.

### 최소 권한 (Least privilege)

필요한 경우 특정 작업에 요구되는 기능으로만 에이전트를 제한할 수 있습니다:

| 리소스 | 제한 옵션 |
| ------------------- | ----------------------------------------------- |
| 파일 시스템 | 필요한 디렉토리만 마운트, 읽기 전용 선호 |
| 네트워크 | 프록시를 통해 특정 엔드포인트로 제한 |
| 자격 증명 | 직접 노출하는 대신 프록시를 통해 주입 |
| 시스템 기능 | 컨테이너에서 Linux 기능(capabilities) 제거 |

### 심층 방어 (Defense in depth)

보안 수준이 높은 환경에서는 여러 제어 요소를 계층화하여 추가적인 보호를 제공합니다. 사용할 수 있는 옵션:

* 컨테이너 격리
* 네트워크 제한
* 파일 시스템 제어
* 프록시에서의 요청 검증

올바른 조합은 위협 모델 및 운영 요구 사항에 따라 달라집니다.

## 격리 기술 (Isolation technologies)

다양한 격리 기술은 보안성, 성능 및 운영 복잡성 간에 서로 다른 절충안(tradeoff)을 제공합니다.

<Info>
  이 모든 구성에서 Claude Code (또는 Agent SDK 애플리케이션)는 격리 경계(샌드박스, 컨테이너 또는 VM) 내부에서 실행됩니다. 아래 설명된 보안 제어 요소는 에이전트가 해당 경계 내부에서 접근할 수 있는 항목을 제한합니다.
</Info>

| 기술 | 격리 강도 | 성능 오버헤드 | 복잡성 |
| ----------------------- | ------------------------------ | -------------------- | ----------- |
| 샌드박스 런타임 | 우수 (안전한 기본값) | 매우 낮음 | 낮음 |
| 컨테이너 (Docker) | 설정에 따라 다름 | 낮음 | 중간 |
| gVisor | 매우 우수 (올바른 설정 시) | 중간/높음 | 중간 |
| VM (Firecracker, QEMU) | 매우 우수 (올바른 설정 시) | 높음 | 중간/높음 |

### 샌드박스 런타임 (Sandbox runtime)

컨테이너 없이 가벼운 격리를 원할 경우, [sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime)은 OS 수준에서 파일 시스템 및 네트워크 제한을 적용합니다.

가장 큰 장점은 단순함입니다: Docker 구성, 컨테이너 이미지 또는 네트워크 설정이 필요하지 않습니다. 프록시 및 파일 시스템 제한 기능이 내장되어 있습니다. 허용된 도메인과 경로를 지정하는 설정 파일만 제공하면 됩니다.

**작동 방식:**

* **파일 시스템**: OS 프리미티브(Linux의 `bubblewrap`, macOS의 `sandbox-exec`)를 사용하여 구성된 경로에 대한 읽기/쓰기 접근 제한
* **네트워크**: 네트워크 네임스페이스를 제거(Linux)하거나 Seatbelt 프로필(macOS)을 사용하여 내장 프록시를 통해 네트워크 트래픽 라우팅
* **구성**: 도메인 및 파일 시스템 경로에 대한 JSON 기반 허용 목록

**설정:**

```bash theme={null}
npm install @anthropic-ai/sandbox-runtime
```

그런 다음 허용된 경로와 도메인을 지정하는 구성 파일을 만듭니다.

**보안 고려 사항:**

1. **동일 호스트 커널**: VM과 달리 샌드박스 처리된 프로세스는 호스트 커널을 공유합니다. 커널 취약점이 있는 경우 이론적으로 탈출이 가능할 수 있습니다. 일부 위협 모델에서는 이것이 수용 가능하지만, 커널 수준의 격리가 필요한 경우 gVisor나 별도의 VM을 사용하세요.

2. **TLS 검사 없음**: 프록시는 클라이언트가 제공한 호스트이름을 기준으로 도메인을 허용 목록에 추가하며 암호화된 트래픽을 종료하거나 검사하지 않습니다. 샌드박스 내부에서 실행되는 코드는 [domain fronting](https://en.wikipedia.org/wiki/Domain_fronting)이나 유사한 기술을 사용하여 허용 목록 외부의 호스트에 도달할 수 있습니다. 위협 모델에 더 강력한 보장이 요구되는 경우 [TLS 종료 프록시](#traffic-forwarding)를 구성하세요. 자세한 내용은 [샌드박스 보안 제한사항](/docs/en/sandboxing#security-limitations)을 참고하세요. 이와 별개로 에이전트가 허용된 도메인에 대한 허용적인 자격 증명을 가지고 있는 경우, 해당 도메인을 사용해 다른 네트워크 요청을 트리거하거나 데이터를 유출하지 못하도록 확인해야 합니다.

많은 단일 개발자 및 CI/CD 사용 사례에서 sandbox-runtime은 최소한의 설정만으로 보안 수준을 크게 향상시켜 줍니다. 아래 섹션에서는 더 강력한 격리가 필요한 배포를 위한 컨테이너 및 VM을 다룹니다.

### 컨테이너 (Containers)

컨테이너는 Linux 네임스페이스를 통해 격리를 제공합니다. 각 컨테이너는 호스트 커널을 공유하면서 파일 시스템, 프로세스 트리 및 네트워크 스택에 대해 독자적인 뷰를 갖습니다.

보안이 강화된 컨테이너 구성은 다음과 같습니다:

```bash theme={null}
docker run \
  --cap-drop ALL \
  --security-opt no-new-privileges \
  --security-opt seccomp=/path/to/seccomp-profile.json \
  --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=100m \
  --tmpfs /home/agent:rw,noexec,nosuid,size=500m \
  --network none \
  --memory 2g \
  --cpus 2 \
  --pids-limit 100 \
  --user 1000:1000 \
  -v /path/to/code:/workspace:ro \
  -v /var/run/proxy.sock:/var/run/proxy.sock:ro \
  agent-image
```

각 옵션의 역할은 다음과 같습니다:

| 옵션 | 목적 |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `--cap-drop ALL` | 권한 승격을 가능하게 할 수 있는 `NET_ADMIN` 및 `SYS_ADMIN` 같은 Linux 기능(capabilities) 제거 |
| `--security-opt no-new-privileges` | setuid 바이너리를 통한 프로세스의 권한 획득 방지 |
| `--security-opt seccomp=...` | 사용 가능한 시스템 호출 제한; Docker 기본값은 ~44개를 차단하며 커스텀 프로필로 더 많이 차단 가능 |
| `--read-only` | 컨테이너의 루트 파일 시스템을 불변(immutable) 상태로 만들어 에이전트가 변경 사항을 보존하지 못하도록 방지 |
| `--tmpfs /tmp:...` | 컨테이너가 정지할 때 지워지는 쓰기 가능한 임시 디렉토리 제공 |
| `--network none` | 모든 네트워크 인터페이스 제거; 에이전트는 아래 마운트된 Unix 소켓을 통해서만 통신 |
| `--memory 2g` | 리소스 고갈 방지를 위해 메모리 사용량 제한 |
| `--pids-limit 100` | 포크 폭탄(fork bomb) 방지를 위해 프로세스 개수 제한 |
| `--user 1000:1000` | 비루트(non-root) 사용자로 실행 |
| `-v ...:/workspace:ro` | 에이전트가 코드를 분석할 수는 있지만 수정하지는 못하도록 읽기 전용 마운트. **`~/.ssh`, `~/.aws`, `~/.config` 같은 민감한 호스트 디렉토리 마운트는 피하세요** |
| `-v .../proxy.sock:...` | 컨테이너 외부에서 실행 중인 프록시에 연결된 Unix 소켓 마운트 (아래 참조) |

**Unix 소켓 아키텍처:**

`--network none`을 사용하면 컨테이너에 네트워크 인터페이스가 전혀 존재하지 않습니다. 에이전트가 외부 세계에 도달할 수 있는 유일한 방법은 호스트에서 실행 중인 프록시에 연결되는 마운트된 Unix 소켓뿐입니다. 이 프록시는 도메인 허용 목록을 적용하고, 자격 증명을 주입하며, 모든 트래픽을 기록할 수 있습니다.

이것은 [sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime)이 사용하는 아키텍처와 동일합니다. 프롬프트 주입으로 인해 에이전트가 침해당하더라도 임의의 서버로 데이터를 유출할 수 없습니다. 도달 가능한 도메인을 제어하는 프록시를 통해서만 통신할 수 있습니다. 자세한 내용은 [Claude Code 샌드박싱 블로그 글](https://www.anthropic.com/engineering/claude-code-sandboxing)을 참고하세요.

| 옵션 | 목적 |
| ---------------- | -------------------------------------------------------------------------------------------------------------------- |
| `--userns-remap` | 컨테이너 루트를 권한이 없는 호스트 사용자에 매핑; 데몬 구성이 필요하지만 컨테이너 탈출 시 피해 제한 |
| `--ipc private` | 크로스 컨테이너 공격 방지를 위해 프로세스 간 통신 격리 |

### gVisor

표준 컨테이너는 호스트 커널을 공유합니다: 컨테이너 내부의 코드가 시스템 호출을 수행할 때 호스트를 실행하는 것과 동일한 커널로 직접 전달됩니다. 이는 커널 취약점이 컨테이너 탈출로 이어질 수 있음을 의미합니다. gVisor는 실제 커널을 거치지 않고 대부분의 시스템 호출을 처리하는 자체 호환성 계층을 구현하여, 유저스페이스에서 시스템 호출을 가로챔으로써 이 문제를 해결합니다.

에이전트가 (프롬프트 주입 등으로 인해) 악성 코드를 실행하는 경우 해당 코드는 컨테이너 내에서 실행되며 커널 취약점 공격을 시도할 수 있습니다. gVisor를 사용하면 공격 표면이 훨씬 줄어듭니다: 악성 코드는 실제 커널에 대한 제한된 접근만 가지며 gVisor의 유저스페이스 구현을 먼저 공격해야 합니다.

Docker와 함께 gVisor를 사용하려면 `runsc` 런타임을 설치하고 데몬을 구성하세요:

```json theme={null}
// /etc/docker/daemon.json
{
  "runtimes": {
    "runsc": {
      "path": "/usr/local/bin/runsc"
    }
  }
}
```

그런 다음 아래 명령으로 컨테이너를 실행합니다:

```bash theme={null}
docker run --runtime=runsc agent-image
```

**성능 고려 사항:**

| 워크로드 | 오버헤드 |
| --------------------- | -------------------------------------------------- |
| CPU 작업 중심 계산 | ~0% (시스템 호출 가로채기 없음) |
| 단순 시스템 호출 | ~2배 느림 |
| 파일 I/O 집중 작업 | 잦은 open/close 패턴 시 최대 10-200배 느림 |

멀티 테넌트 환경이나 신뢰할 수 없는 콘텐츠를 처리하는 경우 추가적인 격리 이점이 오버헤드보다 가치 있는 경우가 많습니다.

### 가상 머신 (Virtual machines)

VM은 CPU 가상화 확장을 통해 하드웨어 수준의 격리를 제공합니다. 각 VM은 고유한 커널을 실행하여 강력한 경계를 생성합니다. 게스트 커널의 취약점이 호스트를 직접 침해하지는 않습니다. 그러나 VM이 gVisor 같은 대안보다 자동으로 "더 안전"한 것은 아닙니다. VM 보안은 하이퍼바이저 및 장치 에뮬레이션 코드에 크게 의존합니다.

Firecracker는 가벼운 마이크로VM 격리를 위해 설계되었습니다. 5 MiB 미만의 메모리 오버헤드로 125ms 이내에 VM을 부팅할 수 있으며, 공격 표면을 줄이기 위해 불필요한 장치 에뮬레이션을 제거했습니다.

이 방식을 사용하면 에이전트 VM에는 외부 네트워크 인터페이스가 존재하지 않습니다. 대신 `vsock`(가상 소켓)을 통해 통신합니다. 모든 트래픽은 vsock을 통해 호스트의 프록시로 라우팅되며, 이 프록시는 요청을 전달하기전에 허용 목록을 적용하고 자격 증명을 주입합니다.

### 클라우드 배포

클라우드 배포의 경우 위의 격리 기술들을 클라우드 네이티브 네트워크 제어와 결합할 수 있습니다:

1. 인터넷 게이트웨이가 없는 프라이빗 서브넷에서 에이전트 컨테이너 실행
2. 프록시로 향하는 트래픽을 제외한 모든 이그레스(egress)를 차단하도록 클라우드 방화벽 규칙(AWS Security Groups, GCP VPC firewall) 구성
3. 요청을 검증하고, 도메인 허용 목록을 적용하며, 자격 증명을 주입하고, 외부 API로 전달하는 프록시(예: `credential_injector` 필터가 적용된 [Envoy](https://www.envoyproxy.io/)) 실행
4. 에이전트의 서비스 계정에 최소한의 IAM 권한을 할당하고, 가능한 경우 프록시를 통해 민감한 접근 권한 라우팅
5. 감사 목적으로 프록시의 모든 트래픽 기록

## 자격 증명 관리

에이전트는 API 호출, 저장소 접근, 클라우드 서비스 상호작용을 위해 자격 증명이 필요한 경우가 많습니다. 과제는 자격 증명 자체를 노출하지 않고 이러한 접근 권한을 제공하는 것입니다.

### 프록시 패턴 (The proxy pattern)

권장되는 접근 방식은 에이전트의 보안 경계 외부에서 프록시를 실행하고, 나가는 요청에 자격 증명을 주입하는 것입니다. 에이전트는 자격 증명 없이 요청을 보내고, 프록시가 이를 추가하여 목적지로 전달합니다.

이 패턴에는 여러 장점이 있습니다:

1. 에이전트가 실제 자격 증명을 전혀 볼 수 없음
2. 프록시가 허용된 엔드포인트 목록을 강제 적용할 수 있음
3. 프록시가 감사를 위해 모든 요청을 기록할 수 있음
4. 자격 증명이 각 에이전트에 분산되지 않고 하나의 안전한 장소에 저장됨

### 프록시를 사용하도록 Claude Code 구성하기

Claude Code는 샘플링 요청을 프록시로 라우팅하는 두 가지 방법을 지원합니다:

**옵션 1: ANTHROPIC_BASE_URL (단순하지만 샘플링 API 요청 전용)**

```bash theme={null}
export ANTHROPIC_BASE_URL="http://localhost:8080"
```

이 방법은 Claude Code 및 Agent SDK가 Claude API로 직접 전송하는 대신 프록시로 샘플링 요청을 전송하도록 지시합니다. 프록시는 일반 텍스트 HTTP 요청을 받아 검사 및 수정(자격 증명 주입 포함)한 다음 실제 API로 전달합니다.

**옵션 2: HTTP_PROXY / HTTPS_PROXY (시스템 전역)**

```bash theme={null}
export HTTP_PROXY="http://localhost:8080"
export HTTPS_PROXY="http://localhost:8080"
```

Claude Code 및 Agent SDK는 이 표준 환경 변수들을 준수하여 모든 HTTP 트래픽을 프록시로 라우팅합니다. HTTPS의 경우 프록시는 암호화된 CONNECT 터널을 생성하므로 TLS 가로채기(interception) 없이는 요청 내용을 보거나 수정할 수 없습니다.

### 프록시 구현하기

자체 프록시를 구축하거나 기존 프록시를 사용할 수 있습니다:

* [Envoy Proxy](https://www.envoyproxy.io/): 인증 헤더 추가를 위한 `credential_injector` 필터가 포함된 프로덕션급 프록시
* [mitmproxy](https://mitmproxy.org/): HTTPS 트래픽 검사 및 수정을 위한 TLS 종료 프록시
* [Squid](http://www.squid-cache.org/): 접근 제어 목록이 포함된 캐싱 프록시
* [LiteLLM](https://github.com/BerriAI/litellm): 자격 증명 주입 및 속도 제한 기능이 있는 LLM 게이트웨이

### 기타 서비스용 자격 증명

Claude API 샘플링 외에도 에이전트는 git 저장소, 데이터베이스 및 내부 API와 같은 다른 서비스에 대한 인증된 접근이 필요한 경우가 많습니다. 두 가지 주요 접근 방식이 있습니다:

#### 커스텀 도구 (Custom tools)

에이전트 보안 경계 외부에서 실행되는 서비스로 요청을 라우팅하는 MCP 서버나 커스텀 도구를 통해 접근 권한을 제공합니다. 에이전트는 도구를 호출하지만 실제 인증된 요청은 외부에서 일어납니다. 도구는 자격 증명을 주입하는 프록시를 호출합니다.

예를 들어 git MCP 서버는 에이전트로부터 명령을 받지만 호스트에서 실행 중인 git 프록시로 전달하며, 이 프록시가 원격 저장소에 접근하기 전에 인증 정보를 추가합니다. 에이전트는 자격 증명을 볼 수 없습니다.

장점:

* **TLS 가로채기 없음**: 외부 서비스가 인증된 요청을 직접 수행
* **외부에 유지되는 자격 증명**: 에이전트는 도구 인터페이스만 보며 기본 자격 증명은 보지 못함

#### 트래픽 포워딩 (Traffic forwarding)

Claude API 호출의 경우 `ANTHROPIC_BASE_URL`을 사용하면 텍스트 상태로 요청을 검사하고 수정할 수 있는 프록시로 요청을 라우팅할 수 있습니다. 하지만 다른 HTTPS 서비스(GitHub, npm 레지스트리, 내부 API)의 경우 트래픽이 엔드투엔드로 암호화되는 경우가 많습니다. `HTTP_PROXY`를 통해 프록시로 라우팅하더라도 프록시는 불투명한 TLS 터널만 볼 수 있어 자격 증명을 주입할 수 없습니다.

커스텀 도구를 사용하지 않고 임의의 서비스로 향하는 HTTPS 트래픽을 수정하려면 트래픽을 복호화하고, 검사 또는 수정한 다음, 전송 전 다시 암호화하는 TLS 종료 프록시가 필요합니다. 다음 단계가 요구됩니다:

1. 에이전트 컨테이너 외부에서 프록시 실행
2. 에이전트의 신뢰 저장소에 프록시의 CA 인증서 설치 (에이전트가 프록시 인증서를 신뢰하도록 함)
3. 프록시를 통해 트래픽이 라우팅되도록 `HTTP_PROXY`/`HTTPS_PROXY` 구성

이 방식은 커스텀 도구를 작성하지 않고도 모든 HTTP 기반 서비스를 처리할 수 있지만 인증서 관리에 따른 복잡성이 추가됩니다.

모든 프로그램이 `HTTP_PROXY`/`HTTPS_PROXY`를 준수하는 것은 아닙니다. 대부분의 도구(curl, pip, npm, git)는 준수하지만 일부는 이 변수들을 무시하고 직접 연결될 수 있습니다. 예를 들어 Node.js `fetch()`는 기본적으로 이 변수들을 무시합니다; Node 24+에서는 `NODE_USE_ENV_PROXY=1`을 설정하여 지원을 활성화할 수 있습니다. 포괄적인 적용을 위해 [proxychains](https://github.com/haad/proxychains)를 사용해 네트워크 호출을 가로채거나, iptables를 구성하여 투명 프록시(transparent proxy)로 아웃바운드 트래픽을 리다이렉트할 수 있습니다.

<Info>
  **투명 프록시(transparent proxy)**는 네트워크 수준에서 트래픽을 가로채므로 클라이언트가 프록시를 사용하도록 별도로 구성될 필요가 없습니다. 일반 프록시는 클라이언트가 명시적으로 연결하고 HTTP CONNECT나 SOCKS로 통신할 것을 요구합니다. 투명 프록시(투명 모드의 Squid나 mitmproxy 등)는 리다이렉트된 순수 TCP 연결을 처리할 수 있습니다.
</Info>

두 방식 모두 TLS 종료 프록시와 신뢰할 수 있는 CA 인증서가 필요합니다. 단지 트래픽이 실제로 프록시에 도달하도록 보장해 줄 뿐입니다.

## 파일 시스템 구성

파일 시스템 제어 요소는 에이전트가 읽고 쓸 수 있는 파일을 결정합니다.

### 읽기 전용 코드 마운트

에이전트가 코드를 분석만 하고 수정할 필요는 없을 때 디렉토리를 읽기 전용으로 마운트합니다:

```bash theme={null}
docker run -v /path/to/code:/workspace:ro agent-image
```

<Warning>
  코드 디렉토리에 대한 읽기 전용 접근조차도 자격 증명을 노출할 수 있습니다. 마운트하기 전에 제외하거나 정제해야 하는 일반적인 파일들:

  | 파일 | 위험 요소 |
  | ------------------------------------------------------- | ------------------------------------- |
  | `.env`, `.env.local` | API 키, 데이터베이스 비밀번호, 시크릿 |
  | `~/.git-credentials` | 평문 상태의 Git 비밀번호/토큰 |
  | `~/.aws/credentials` | AWS 액세스 키 |
  | `~/.config/gcloud/application_default_credentials.json` | Google Cloud ADC 토큰 |
  | `~/.azure/` | Azure CLI 자격 증명 |
  | `~/.docker/config.json` | Docker 레지스트리 인증 토큰 |
  | `~/.kube/config` | Kubernetes 클러스터 자격 증명 |
  | `.npmrc`, `.pypirc` | 패키지 레지스트리 토큰 |
  | `*-service-account.json` | GCP 서비스 계정 키 |
  | `*.pem`, `*.key` | 개인키 (Private keys) |

  필요한 소스 파일만 복사하거나 `.dockerignore` 형태의 필터링을 사용하는 것을 고려하세요.
</Warning>

### 쓰기 가능한 위치

에이전트가 파일을 써야 하는 경우, 변경 사항을 지속할지 여부에 따라 몇 가지 옵션이 있습니다:

컨테이너의 일회성 워크스페이스의 경우 메모리에만 존재하고 컨테이너가 정지하면 지워지는 `tmpfs` 마운트를 사용하세요:

```bash theme={null}
docker run \
  --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=100m \
  --tmpfs /workspace:rw,noexec,size=500m \
  agent-image
```

변경 사항을 유지하기 전에 검토하고 싶다면 오버레이 파일 시스템(overlay filesystem)을 사용하여 기본 파일을 수정하지 않고 에이전트가 쓰기를 수행할 수 있도록 하세요. 변경 사항은 검사, 적용 또는 폐기할 수 있는 별도의 계층에 저장됩니다. 완전한 영구 출력을 원한다면 전용 볼륨을 마운트하되 민감한 디렉토리와는 분리해 두세요.
